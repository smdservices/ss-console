# Operator Legibility & Configurability — Ground-Truth Matrix

**Status:** Accepted — Phase 0 signed off (2026-07-07).
**Companion to:** [ADR 0069](../../adr/0069-operator-legibility-progressive-configurability.md).
**Purpose:** The single source of truth for the operator-page redesign build. Every facet's real/stub/needs-wiring/needs-schema state, verified against code (four ground-truth sweeps + firsthand reads, 2026-07-07). A build slice may not claim a facet "done" until its **Verified-live** cell has an evidence reference (a `crane_verify` id from a real seat).

This matrix is the anti-theater device. It exists because a page-by-page audit found the recurring failure mode: surfaces that render but don't carry data, and config forms that log intent but never persist. Both are recorded here as facts, not surprises.

---

## The two data planes (the fact that gates everything)

Operator data lives in **two disconnected databases**, and which one a facet lives in decides whether a viewer can be built REAL today:

| Plane                 | Where                                               | Written by                                                                                         | Reachable from the console today?                                                                                                            |
| --------------------- | --------------------------------------------------- | -------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| **Config projection** | central ss-console D1 `customer_configs`            | CI on merge (`scripts/project-customer-config.ts`, `src/lib/portal/customer-config-projection.ts`) | **Yes** — `getCustomerConfig` reads it directly                                                                                              |
| **Runtime mirror**    | each customer's own Machine D1 (`hermes-{slug}-d1`) | overlay plugins inside the Machine                                                                 | **Only** via the ADR 0043 HTTP read seam, **gated behind `OPERATOR_RUNTIME_READ_URL` + `_SECRET` — currently unset (fails closed to empty)** |

Config-plane facets are buildable REAL now (contingent on the seat's `customer_configs` row being populated — it is "hand-seeded during alpha," so verification is per-seat). Runtime-plane facets need the ADR 0043 seam wired **and** a consuming resolver (some also need a new read-kind) before any viewer is more than a stub.

**The projection is lossy by design.** `customer_configs` carries only: `personas_json` (narrowed — `version`/`enabled`/`cost_estimate`/`scope`/**`cron`**/**`bundles`** are dropped), `voice_library_json`, `escalation_json`, `business_hours_json`, `connectors_json`, `scope_json`, `authority_json`, `credential_custody_default`, `mcp_connector_json`, `compliance_enabled`, `vertical`. Anything else authored in `customer.yaml` (cron, bundles, memory, safety, digest, relationship, telegram, webhook_triggers) is **not in the projection** and must be read from R2/git or added to the projection.

**Canonical schema source:** `src/lib/operator/customer-yaml/types.ts` (`CustomerYaml`) + `operator/contracts/customer-yaml-blocks.yaml`. The prose spec `docs/specs/operator/customer-yaml-schema.md` is **stale** (still shows the retired scalar `trust_ceiling` model) — do not build from it.

## Tiering

- **Tier 1 — REAL NOW (config projection).** A shared viewer can be built and verified against central D1 today.
- **Tier 2 — RUNTIME (needs the ADR 0043 seam wired + a resolver; some need a new read-kind).**
- **Tier 3 — NEEDS SCHEMA (no config facet exists; design one first).**
- **Tier 0 — THE WRITE-BACK SPINE.** Cross-cutting. Every "configurable" surface depends on it and it is unbuilt.

## What already exists (the good news)

- **The managed→self-managed spectrum is a built data model + resolver** — `src/lib/operator/authority.ts` (ADR 0041) + `src/lib/portal/operator/domain-surface.ts`. `managed` (all client switches off) is the launch default; `self_managed` flips them; per-domain overrides. SMD control is always retained (additive). The build wires write-back + per-facet operable mounts, it does not invent the model.
- **Most config-inspection views exist on the admin side already** — `governance.astro` (editable exposure matrix), `authority.astro`, `connectors.astro`, `config.astro`, `memory.astro`. They and the portal are **parallel duplicate implementations over a shared foundation** (`config-governance.ts`, `credential-custody.ts`, `authority.ts`, `customer-config.ts`). Two governance labelers, two connector parsers, two custody labelers, two authority renderers — exactly the "one viewer, two mounts" target.
- **Config-plane facets are real today** — skills toggles/initiation, entitlements/exposure, voice library, scope, hours, connections, escalation, authority, compliance retention. The viewers can be built and verified against central D1 now.

## What is genuinely missing (the honest gaps)

1. **Write-back (Tier 0)** — nothing persists config edits to source of truth. Foundational; front-load it.
2. **Workflow schema (Tier 3)** — the flagship view has no config facet at all; a generic (vertical-neutral) schema must be designed first.
3. **Schedule projection (Tier 2-adjacent)** — authored crons exist but are dropped from the projection; needs a projection extension.
4. **Runtime seam (Tier 2)** — Activity, Memory, agent-authored skills, job execution, runtime voice all wait on `OPERATOR_RUNTIME_READ_URL`; Memory/skills/jobs also need resolvers.
5. **The duplication** — collapse the parallel admin/portal facet renderers into one shared viewer each.
