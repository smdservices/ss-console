**Spec for issue #802.** What's in the exportable compliance packet. Susan-readable: outside counsel who is not technical must be able to read this end-to-end and confirm the agent did what we claim. Design constraint per UX Lead: plain-language first-page summary, then the technical artifacts.

## Contract

### Packet structure

The packet is a zip at `{slug}/audit-exports/compliance-packet-{ts}.zip` per r2-vectorize-naming.md. Generated by the `compliance-audit-export` skill (§8.2). Customer requests via dashboard Audit tab → "Generate compliance packet". Result emailed within ≤60s per §17.1 audit-log-request SLA.

```
compliance-packet-2026-05-20T14-30-00Z.zip
├── 00-README.md                  # ← The plain-language first page
├── 01-summary.pdf                # ← Auto-rendered Susan-readable narrative
├── 02-architecture-controls.md   # ← The three controls (§13.1) verified
├── 03-audit-log.csv              # ← Structured audit_log dump
├── 04-audit-log-human.md         # ← Same data, grouped + narrated by Captain
```

### 00-README.md (the plain-language first page)

Template:

```markdown
# Compliance Evidence — {firm-name}

**Period covered:** {start-date} to {end-date}
**Generated:** {generation-ts}
**Generated by:** Scott Durgan (SMDurgan, LLC), operating "Marcus" on behalf of {firm-name}

This package documents how the AI Employee named "{persona-name}" operated
inside {firm-name}'s practice during the period above. It is meant to be
read by an attorney advising {firm-name} on AI governance, by an outside
auditor reviewing the firm's compliance posture, or by the firm itself.

You do not need a technical background to read this package. The first
two documents (this README and the summary PDF) are written for general
counsel. The remaining documents are the underlying evidence, in case
you want to verify specific claims.

## What this package proves

1. **The agent never sent communications externally.** Every external send
   was performed by a named human reviewer pressing send from their own
   email account. See §03 (audit log) and §02 (architectural controls).

2. **The agent operated only within the scope the firm authorized.**
   The firm's scope rules (which folders, which clients, which keywords
   block access) are reproduced in §05. The audit log records every read
   the agent performed.

3. **The agent's knowledge of the firm is documented.** Every rule the
   agent learned, every person it knows about, every voice sample it
   was trained on — captured in §06.

4. **The agent's safety substrate verified on every boot.** Eight
   architectural safety checks ran on every restart of the agent's
   computer. See §09.

5. **Customer data never trained a public model.** The platform's
   architectural controls (§02) verify the closed-loop posture.
   The signed DPA in §10 makes this a contractual commitment.

## Questions?

Contact: scott@smd.services
```

### 01-summary.pdf

Auto-rendered from a markdown template. Contents:
- "What the agent did" summary (drafts created / approved / rejected per skill, week-by-week)
- "What the agent learned" summary (memory edits per category, voice violations caught)
- "What the agent never did" summary (an exhibits list: zero external sends, zero data leaks, zero invariant violations — quoted from audit_log)
- "What the firm controlled" summary (trust ceilings configured, scope blocks active, users in each role)

Layout: 1 page per section, max 8 pages. Captain reviews before delivery — auto-generated content is a draft; Captain may edit the markdown source and re-render.

### 03-audit-log.csv

Full `audit_log` table dump for the period, exported via D1 to CSV. Columns:

```
id, ts, action_type, actor, actor_role, skill_name, matter_ref,
input_digest, output_digest, diff_digest, trust_ceiling, metadata
```

Digests not resolved (auditor verifies digest matches the underlying R2 object on request — keeps substantive content out of the packet by default).

### 04-audit-log-human.md

Narrated audit log. Events grouped by week, then by category (drafts / memory / trust / connectors / invariants / escalations). Captain reviews and may add inline annotations for noteworthy events. Generated from a markdown template using the CSV in §03.

### 05-customer-yaml.redacted.yml

The full `customer.yaml` with these fields redacted (replaced by `<redacted>`):
- All `token_ref` values
- All `oauth_scopes` values (replaced by count: `<12 scopes redacted>`)
- All `escalation.failure_recipients` and `red_flag_recipients` email addresses (replaced by domain: `<redacted>@firm.example.com`)

Everything else — persona, vertical, skills enabled, trust ceilings, scope rules — is shown.

### 06-memory-snapshot.json

JSON dump of:
- `memory_rules` rows (rule content visible — rules are customer-curated, intentionally readable)
- `person_mappings` rows (names + roles visible; external IDs redacted)
- `voice_samples` metadata (ID, upload date, cohort, sanitization flag — sample content NOT included in default packet; available on request via separate signed export)
- `recipient_cohorts` rows

### 07-skill-catalog.json

For each skill enabled during the period:
- `skill_name`, `content_hash` (pinned version), `activated_at`, `trust_ceiling`, `run_count`
- Citation to the skill's `SKILL.md` content as committed in git (commit SHA + path)

### 08-engagement-letter-clauses/

Markdown copies of the per-state engagement-letter AI disclosure clauses the firm uses. Per `customer.yaml.vertical` (law-firm) + `customer.yaml.practice_areas` + the firm's home state. Pennsylvania, Utah, and the firm's home state are always included.

### 09-boot-checks.csv

Full `invariant_boot_checks` dump. Columns: `id, ts, invariant_num, passed, failure_detail`. Every Machine boot during the period present. Zero failure rows is the happy path.

## Failure modes

- **Period exceeds retention window**: packet covers only available retention period (90 days default per §13.3, or whatever customer paid for). Out-of-window data not included; README explicitly notes the period.
- **Customer-yaml redaction misses a secret**: pre-export validator runs `customer-yaml-secret-scan.sh` from customer-yaml-schema.md against the redacted output. Match → export aborts with stderr.
- **Captain signature key not available**: export aborts; alert Captain to either provide signing key or generate unsigned packet (the latter marked clearly in manifest).
- **R2 zip exceeds 1GB**: split into multi-part archive; manifest lists all parts; Captain ships sequentially or via signed-URL bundle.

## Verification

1. **Round-trip test** at `tests/ai-employee/compliance-packet.test.ts`: fixture customer with 30 days of audit log; generate packet; assert every documented file present, hashes valid, signature verifies, README placeholders all substituted.
2. **Redaction test**: fixture customer.yaml with deliberately-placed secret pattern; assert export aborts with secret-pattern stderr (does NOT echo the value).
3. **PDF render test**: assert 01-summary.pdf renders within 60s for a 30-day period and is ≤8 pages.
4. **Reader test (manual, pre-launch)**: Captain hands the packet to outside counsel (a non-technical attorney) for read; gather feedback on clarity. Baseline before customer #1.

## Implementation notes
